
# DPO: Derivation and Intuition

> This document derives the DPO objective from first principles,
> explains each step's significance, and states where the intuition
> is deepest. Written to be reproduced on a whiteboard in 10 minutes.

---

## 1. The RLHF objective we are trying to solve

We want a language model π that is helpful (maximises a reward r)
while staying close to a reference policy π_ref (the SFT checkpoint).
The KL penalty prevents reward hacking:
```

max_π  E_{x~D, y~π(·|x)} [ r(x,y) ]  −  β · D_KL[ π(y|x) ‖ π_ref(y|x) ]

```
β controls the trade-off: small β → more reward, more drift;
large β → less drift, less reward.

---

## 2. The closed-form optimal policy

This objective has a known analytic solution (standard result from
KL-regularised optimal control):
```

π*(y|x)  =  (1 / Z(x))  ·  π_ref(y|x)  ·  exp( r(x,y) / β )

```
where Z(x) = Σ_y π_ref(y|x) · exp(r(x,y)/β) is the partition function.

**The problem:** Z(x) requires summing over all possible sequences y,
which is exponentially large and completely intractable. This is why
PPO-based RLHF requires rollouts — it approximates the optimum by
climbing toward it with sampled sequences.

---

## 3. DPO's move: rearrange, don't sample

Solve for r from the optimal-policy expression:
```

r(x,y)  =  β · log π*(y|x)  −  β · log π_ref(y|x)  +  β · log Z(x)

```
Now substitute into the **Bradley–Terry preference model**, which says:
the probability that y_w (the preferred response) is chosen over y_l is
```

p(y_w ≻ y_l | x)  =  σ( r(x,y_w)  −  r(x,y_l) )

```
The reward difference is:
```

r(x,y_w) − r(x,y_l)
  = β·log π*(y_w|x)/π_ref(y_w|x)
  − β·log π*(y_l|x)/π_ref(y_l|x)

+ β·log Z(x)  −  β·log Z(x)
  ──────────────────────────────────

 ```
  The Z(x) terms cancel (same x for both responses).



So:

```
p(y_w ≻ y_l | x)  =  σ( β·log π*(y_w|x)/π_ref(y_w|x)
                       − β·log π*(y_l|x)/π_ref(y_l|x) )
```

**This expression has no r(·) and no Z(x).** The intractable reward
and partition function have been eliminated algebraically.

---

## 4. The DPO loss

Replace the optimal π* with the parameterised π_θ and take the
negative log-likelihood over the dataset D of preference pairs:

```
L_DPO(θ)  =  − E_{(x, y_w, y_l) ~ D} [
    log σ(
        β · log π_θ(y_w|x) / π_ref(y_w|x)
      − β · log π_θ(y_l|x) / π_ref(y_l|x)
    )
]
```

**That's the entire method.** No reward model. No rollout loop.
No value function. A cross-entropy loss over a static dataset — which
is why it runs on a T4 while PPO typically requires 8× A100s.

---

## 5. The implicit reward

Define the **implicit reward** of a response under the current policy:

```
r̂_θ(x, y)  =  β · log π_θ(y|x) / π_ref(y|x)
```

This is computable from the model's own log-probabilities.
The DPO loss is then:

```
L_DPO(θ)  =  − E [ log σ( r̂_θ(x, y_w) − r̂_θ(x, y_l) ) ]
```

In the training logs, `rewards/chosen` = mean r̂(y_w),
`rewards/rejected` = mean r̂(y_l), and `rewards/margin` is their difference.

---

## 6. The gradient: why DPO is self-curriculising

```
∇_θ L  =  − β · E[
    σ( r̂_θ(y_l) − r̂_θ(y_w) )          ← weight: large when currently wrong
    · ( ∇_θ log π_θ(y_w|x)              ← increase chosen log-prob
        − ∇_θ log π_θ(y_l|x) )          ← decrease rejected log-prob
]
```

The sigmoid weight `σ(r̂_l − r̂_w)` is large when the implicit reward
model ranks the pair incorrectly (rejected > chosen) and small when it
already ranks them correctly. **DPO automatically concentrates learning
on the pairs it currently gets wrong.** This is a self-curriculising
property that emerges from the loss structure.

---

## 7. The implicit KL divergence

The KL from π_θ to π_ref can be approximated from available quantities:

```
D_KL(π_θ ‖ π_ref)  ≈  E[ (r̂(y_w) + |r̂(y_l)|) / (2β) ]
```

This is logged as `implicit_kl` in AlignForge's training callbacks.
It costs no additional forward passes — just arithmetic over already-
computed reward scalars.

**What to watch:** if KL grows without plateau, the policy is drifting
toward reward hacking. β should be increased or training stopped early.

---

## 8. When PPO beats DPO

DPO is **off-policy**: it trains only on pre-collected preference data.
If that data was generated by a model much weaker than the current policy,
the chosen/rejected distinction may be uninformative (both responses are
good by the current policy's standards).

PPO is **on-policy**: it generates its own responses at each step, so the
preference labels are always meaningful relative to the current policy.

**When to prefer PPO:**

- Heavy compute available (8+ GPUs).
- Online reward signal from a strong reward model.
- The preference data distribution is very narrow.

**When DPO is correct (which is most cases at portfolio scale):**

- Single GPU.
- Static preference dataset.
- Stability is more important than ceiling quality.

---

## 9. Alternatives to standard DPO

| Method         | Key difference                          | When to use                            |
| -------------- | --------------------------------------- | -------------------------------------- |
| **ORPO**       | Merges SFT + preference into one stage  | When you can't separate the two stages |
| **SimPO**      | Removes the reference model entirely    | When you want minimal memory           |
| **KTO**        | Uses binary good/bad labels, not pairs  | When pairs are hard to collect         |
| **Online DPO** | Iteratively regenerates preference data | When you have a strong reward model    |
